1. Prefixe tudo — inclusive o inglês. Não deixe o padrão sem prefixo.

2. YAML + tag própria: concordo com a conclusão, discordo do motivo citado — e faltam dois reforços

O motivo que vocês deram ("gettext falha aberto") é verdade, mas é corrigível: dá para escrever uma checagem de paridade sobre .po também (existe polib, é só Python). O que NÃO é fácil de corrigir — e é o motivo real para preferir YAML no seu contexto — são duas coisas de infraestrutura:

Dependência de binário do sistema operacional. makemessages precisa do xgettext e compilemessages precisa do msgfmt — ferramentas GNU instaladas no SO, não algo que pip install resolve. Todo agente/runner precisa ter isso disponível e no PATH. YAML via PyYAML é só uma dependência Python, roda em qualquer sandbox sem setup de sistema.
Passo de build. Django precisa de .mo compilado para servir tradução em runtime — ou você versiona binário no Git (diff ilegível, quebra a cultura de PR pequeno e revisável) ou adiciona compilação ao pipeline de deploy. Isso é exatamente o "passo manual recorrente" que seu critério de sustentabilidade rejeita. YAML é ao mesmo tempo fonte e artefato de runtime — nunca compila.

Dito isso, o comportamento permissivo do gettext é real e reconhecido pelos próprios mantenedores do Django como uma limitação sem solução fácil embutida — é um comportamento por design que deixa erro passar silenciosamente, e não há muito que o framework consiga fazer a respeito de forma nativa. Tem até uma pegadinha específica documentada: variantes de inglês têm tratamento especial no gettext do Django, e depender do idioma padrão como fallback pode devolver o msgid cru em vez do texto esperado. E tem uma descoberta recente relevante para o seu caso específico (agentes de IA traduzindo): quando uma tradução tem placeholder incompatível com o original — um erro comum em tradução automática que não entende a semântica do placeholder — o compilemessages pode simplesmente descartar a entrada em silêncio. Isso é exatamente o tipo de erro que um agente cometeria (traduzir errado o nome dentro de %(nome)s) e o gettext responde a isso descartando, não reprovando. Reforça sua decisão, não enfraquece.

O que você realmente perde, item por item (vocês listaram plurais, interpolação e RTL):

Interpolação: não é privilégio do gettext — é formatação de string comum. Sua própria tag {% t %} resolve isso com .format(). Não perde nada aqui.
RTL: também não é feature do gettext — é CSS/HTML (dir, propriedades lógicas). O flag LANGUAGE_BIDI do Django é só um booleano por locale; vira mais um campo no seu registro de sites (dir: rtl), nada mais. Não perde nada real aqui também.

3. Namespace por página — mas isolamento físico de arquivo, não só de chave interna

Namespace dentro de um YAML único por idioma (en.yaml com cadastro.titulo, checkout.titulo) evita colisão de chave, mas não evita conflito de merge — dois agentes trabalhando em páginas diferentes ainda tocam o mesmo arquivo. Vá um passo além: um diretório por página, um arquivo por idioma dentro dele (traducoes/cadastro/en.yaml, traducoes/cadastro/pt-br.yaml, traducoes/checkout/en.yaml...). Isso torna conflito de merge entre páginas diferentes estruturalmente impossível, não só improvável — e é a mesma lógica de isolamento que já rege a arquitetura de células de vocês, só aplicada um nível abaixo. Também mantém o raio de alcance de qualquer edição de agente limitado a uma página só, o que ajuda tradução automática (o agente tradutor vê só o vocabulário de uma página por vez, contexto mais limpo) e mantém o diff dentro do teto de 15 arquivos do CI mesmo conforme o número de páginas cresce para dezenas.

Evite: um único arquivo por idioma crescendo para sempre — funciona com 5 páginas, vira gargalo de merge com 30.

4. Fallback só entre variantes da mesma língua — nunca entre idiomas diferentes

Aqui eu separaria dois conceitos que o desenho atual trata como um só. Idiomas-base (en, pt-br, es) mantêm a regra que vocês já têm: paridade total obrigatória, sem fallback — porque não existe fallback seguro entre idiomas não relacionados (mostrar inglês para quem devia ver espanhol não é fallback, é bug fantasiado de fallback). Variantes regionais (pt-pt sobre pt-br, e futuramente en-gb sobre en-us) são outra categoria: modele como pt-br + um arquivo de sobreposição só com o que difere de verdade (vocabulário, "tu" vs "você"), não uma cópia completa. Adicione um campo fallback_locale no registro de sites/idiomas (null para idiomas-base, apontando para pt-br no caso de pt-pt).

A checagem de CI muda de "toda chave existe neste idioma" para "toda chave usada por este idioma existe na cadeia (arquivo próprio ∪ fallback)" — o conteúdo entregue ao usuário continua com paridade de 100% garantida, mas o custo de lançar pt-pt no dia 1 é um arquivo vazio, que já é válido e completo por herdar tudo de pt-br. É assim que grandes projetos multilíngues (Firefox/Mozilla l10n, por exemplo) tratam variante regional — não é algo bespoke que vocês estariam inventando.

Prós: lançar variante nova fica barato de verdade — arquivo vazio é um pt-pt válido no dia 1, chaves específicas entram uma a uma conforme alguém notar diferença real. Contras: a checagem de CI fica um pouco mais complexa (resolver cadeia em vez de comparação plana) — mas é custo único de construir o teste, não trabalho manual recorrente, então cabe na sua cultura. Vale também expor um relatório simples de "quanto % do pt-pt já foi sobrescrito" para que herdar de pt-br seja um estado visível e intencional, não uma surpresa.

5. O que já está certo, o que falta, o que é mito

Canonical por idioma (item 5) está certo — o erro clássico é canonical de toda tradução apontando de volta para o inglês, que diz ao Google "isso é duplicado, indexe só o inglês" — o oposto do que vocês querem. Vocês já evitaram essa armadilha.

O que falta mecanicamente: hreflang precisa ser auto-referenciado e recíproco — toda versão de idioma precisa listar a si mesma, além de todas as outras versões, e se a página A referencia a página B como alternativa, B precisa referenciar A de volta. Isso só fica garantido se a emissão de hreflang for gerada a partir do mesmo dado declarativo do registro de sites/idiomas (ponto 4 do desenho de vocês) — nunca escrita à mão por página, porque aí diverge silenciosamente conforme páginas são adicionadas. Vale o esforço: um estudo com quase 375 mil domínios encontrou problema de hreflang em 67% deles, mais da metade sem a tag x-default — é o tipo de erro que praticamente todo mundo comete quando faz na mão. 
Medium + 2

Sitemap por idioma: não é mito, mas não é urgente para uma página só — vira valioso a partir de umas dezenas de URLs; gere a partir do mesmo registro quando chegar lá, nunca mantenha manual. Content-Language (header HTTP): mais perto de mito do que de essencial — Google historicamente dá pouco peso a esse header, hreflang é o que importa de verdade; não vale esforço de engenharia extra se a arquitetura de vocês tornar isso incômodo. Mito real a descartar: que conteúdo traduzido com o mesmo layout/menu conta como "conteúdo duplicado" — não conta, hreflang existe exatamente para esse padrão.

6. Roteamento: usem o i18n_patterns do Django dentro de cada célula — não reinventem isso no Traefik

Essa é a peça mais arriscada tecnicamente das oito, porque mistura duas preocupações que dá para separar. Você não precisa escolher entre "todo o i18n do Django" e "totalmente próprio" — pegue só o pedaço de roteamento por prefixo, que é desacoplado do gettext:

i18n_patterns() + LocaleMiddleware existem exatamente para prefixo de idioma na URL e detecção de idioma ativo — e não dependem de .po/.mo existir. Se a célula não usa gettext()/{% trans %} em lugar nenhum (porque vocês vão usar {% t %} lendo YAML), o subsistema de catálogo de tradução do Django simplesmente não entra em cena — só a parte de parsing de URL e request.LANGUAGE_CODE é usada. Essa API é estável há muitas versões — confirmei que está presente e documentada da mesma forma do Django 4 ao 6.2 em desenvolvimento, não é algo instável entre versões.
No Traefik: a regra de prefixo de cada célula (PathPrefix('/checkout')) precisa aceitar também um segmento opcional de idioma antes (regex tipo /{lang:[a-z]{2,3}(-[a-z]{2})?}/checkout OU /checkout) — mudança mecânica e simétrica em todas as células, idealmente gerada a partir do mesmo registro de idiomas em vez de mantida à mão célula por célula.
Não decapem o prefixo no gateway. Encaminhem o path original completo para a célula, e deixem o i18n_patterns de dentro da própria célula (Django) fazer o strip/detecção — isso é literalmente o trabalho para o qual essa API foi feita, é código testado e mantido pelo core do Django em vez de regex artesanal no Traefik, e mantém a chave de cache = URL completa (se decapar antes do cache decidir, dois idiomas colidem no mesmo cache).
Bônus de graça: quando i18n_patterns está em uso e a URL chega sem prefixo, o LocaleMiddleware já redireciona automaticamente para a versão com prefixo detectado (cookie, depois Accept-Language) — é o comportamento que a pergunta 1 estava pedindo, e vocês ganham sem escrever nada custom.

O que os grandes multissites fazem, na prática: idioma como segmento mais externo do path (não depois do prefixo de seção/serviço — ninguém organiza assim, porque "em que idioma é essa visita" é uma dimensão de fora para dentro, não um detalhe por célula) e cada serviço de borda aceita o prefixo opcionalmente antes de rotear internamente. Subdomínio por idioma eu descartaria para vocês especificamente: multiplicaria hosts que o catálogo de sites precisa conhecer, e "idioma é dado, não infraestrutura" (ponto 4 do desenho) deixa de valer.

7. Dados traduzíveis (nome de produto/oferta): campo JSON por locale — com uma rede de segurança que o CI de vocês não alcança

Diferente de copy de UI: esse conteúdo normalmente é criado/editado por admin (não necessariamente via PR de agente), e o volume cresce no ritmo do negócio, não no ritmo de deploy. Recomendo campo JSONField por linha ({"en": "...", "pt-br": "...", "es": "..."}) em vez de tabela de tradução genérica — menos infraestrutura nova, natural em Postgres, sem join extra para ler todos os idiomas de uma linha de uma vez. Serviço dedicado de tradução é over-engineering para o tamanho atual do problema — deixe isso para quando (se) existir workflow de tradutor/revisão de verdade.

O ponto que importa mais que a escolha do formato: a esteira de CI fail-closed de vocês é um mecanismo de git/PR — no momento em que conteúdo traduzível mora em banco editado por admin, essa rede de segurança simplesmente não alcança mais aquele dado. Não existe merge para bloquear. Isso pede um mecanismo diferente, deliberado: validação no nível do admin/model (recusar salvar um produto sem nome em todo idioma obrigatório) e/ou um comando de auditoria periódico que reporta lacuna de idioma no banco. Não é a mesma ferramenta reaproveitada — é uma ferramenta nova, e vale desenhar isso de propósito em vez de assumir que o CI de arquivo também cobre isso.

8. O que é barato agora e caro depois, com 10+ idiomas

Na ordem de impacto:

UTF-8 em tudo, sem exceção — banco, resposta HTTP com charset explícito, todo arquivo de template e tradução. Praticamente grátis para garantir agora com um teste mecânico; mistura de encoding entre arquivo antigo e novo é uma fonte clássica de bug de cauda longa.
Tamanho de texto na UI — alemão, português e finlandês costumam ser 30–50% mais longos que inglês para o mesmo sentido. Componentes construídos com largura fixa pensando só em uma língua quebram visualmente quando a segunda ou terceira chega. Teste botão/rótulo/nav com string deliberadamente longa antes mesmo de ter tradução real (pseudo-localização), não depois.
Propriedades lógicas de CSS (margin-inline-start em vez de margin-left) em todo CSS novo — custo zero escrever assim desde já, e deixa RTL futuro (se um dia vier) funcionando na maior parte sem reescrever nada.

Sem depender de string hand-rolled por idioma, que vira fazenda de bug a partir do idioma número 4 ou 5.

As quatro têm a mesma raiz: idioma é uma preocupação transversal — atravessa toda célula, toda página, todo request. A arquitetura de vocês foi otimizada para o oposto: isolamento estrito entre células, diff pequeno e independente por PR. Toda vez que uma preocupação transversal encontra uma arquitetura em silo, aparece atrito na borda. Foi isso que apareceu:

A. A checagem de paridade (item 3) tem um ponto cego que eu identifiquei e não escrevi. Paridade entre idiomas pega "existe em pt-br mas falta em es". Ela NÃO pega "chave usada num {% t %} do template mas que não existe em idioma nenhum" — um agente digita {% t "cadastro.titulo_errdo" %} com typo, e como a chave está ausente nos dois idiomas igualmente, o conjunto-diferença dá zero. Passa no CI, quebra em produção. Isso pede uma checagem estruturalmente diferente, não mais do mesmo: varrer todos os usos de {% t "..." %} nos templates e cruzar contra a união de chaves que existem em pelo menos o idioma-base. Uso sem definição em lugar nenhum = falha de CI. E é esse blind spot específico — não a divergência entre idiomas, que o CI já bloqueia por completo — que justifica o fallback silencioso pro inglês em produção existir como rede de segurança: ele não é para o caso comum, é para esse caso residual.

B. Como uma página nova nasce em 3 idiomas ao mesmo tempo sem violar paridade nem o teto de 15 arquivos. A primeira página de meshcraft.top precisa nascer em en+pt-br+es simultaneamente. Com a estrutura de arquivo-por-página-por-idioma (pergunta 3), isso é só 3 arquivos novos — cabe folgado no teto. O ponto que eu não deixei explícito: a PR que introduz uma página só deveria ser aceita quando os arquivos de TODOS os idiomas que o site já declara chegam juntos — não existe estado intermediário de "página meio traduzida" mergeado. Isso é diferente de adicionar um idioma novo a uma página que já existe há meses, onde granularidade de um arquivo por vez faz sentido. São dois fluxos de PR distintos e vale nomear os dois separadamente para os agentes.

C. Link entre células perde o prefixo de idioma — e Django não resolve isso sozinho. Dentro de UMA célula, i18n_patterns faz {% url %} devolver a URL já com o prefixo certo, automático. Mas suas células são serviços Django separados — containers, bancos e contratos OpenAPI distintos, por desenho. Quando o template da célula "funil" (multilíngue) linka para "checkout" (hoje não multilíngue, ou será depois), não existe reversão automática entre serviços — Django resolve URL só dentro do próprio urlconf. Um link cadastro→checkout escrito sem pensar nisso hoje vai ou perder o idioma no meio do funil, ou quebrar quando checkout também virar multilíngue. Isso pede uma convenção explícita agora — um helper que monta a URL cross-célula a partir do host-base no registro de sites, prependando o idioma ativo manualmente — porque não tem correção automática de framework aqui. Vale decidir antes de checkout precisar de i18n, não depois.

D. Ligar um idioma-base novo (não variante) num site já grande estoura o teto de 15 por construção. A estrutura de arquivo-por-página funciona linda para desenvolvimento incremental, mas "habilitar francês pra valer" num site com 40 páginas exige 40 arquivos novos de conteúdo real de uma vez — diferente de variante regional, que nasce vazia via fallback_locale (ponto 4 da minha resposta anterior). Isso não é opcional nem gradual: cada página precisa ter conteúdo francês real antes de ficar visível nesse idioma. Duas saídas, e vale escolher qual agora: (1) sequenciar em várias PRs pequenas, habilitando o idioma para um subconjunto de páginas por vez, só virando a flag "habilitado" no registro depois que todas passarem — o idioma existe nos bastidores mas não é servido até lá; ou (2) um tipo de PR expresso, reconhecidamente em lote, isento do teto de 15 e revisado de forma diferente (paridade automatizada em vez de revisão linha a linha). As duas têm implicação diferente no workflow dos agentes, e nenhuma das duas está errada — só precisa ser escolhida de propósito, não descoberta na hora que alguém tentar lançar um idioma novo e o CI travar.
